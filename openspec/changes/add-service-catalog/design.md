# Design: Add the service catalog

## Context

The repository has no application code yet, so this change also creates the
application every later change builds on (see proposal.md for why). The
project-wide stack (Java 21, Spring Boot 4, Gradle, PostgreSQL, Flyway,
Testcontainers) is fixed in `openspec/config.yaml`; this document covers the
choices within it. The development machine has JDK 21 but no Docker runtime yet,
and both local PostgreSQL and the integration tests need one.

## Goals / Non-Goals

**Goals:**

- A conventional Spring Boot layout that a reviewer can navigate quickly and that
  later features slot into without restructuring.
- Every spec scenario covered by an automated test, with database behavior tested
  against a real PostgreSQL.
- One command each to run, test, and build.

**Non-Goals:**

- Abstractions for entities that don't exist yet: base entity classes, generic
  CRUD services, or a multi-module build.
- Optimistic locking, caching, or asynchronous processing. With one local user
  they solve problems DevPlane doesn't have.

## Decisions

### 1. One Spring Boot application, organized by feature

A single Gradle project at the repository root, base package
`io.github.spollito.devplane`, with one package per feature:

```
io.github.spollito.devplane
├── catalog/   controller, request/response records, ServiceCatalog, entity, repository
└── api/       exception handler and shared API types such as PageResponse
```

Later features (`templates`, `deployments`, ...) become sibling packages.

- *Package by layer* (`controllers/`, `services/`, ...) was rejected: it scatters
  each feature across the tree, and that gets worse with every feature.
- *Hexagonal architecture* was rejected as too much ceremony for CRUD.

The domain word "service" collides with Spring's `@Service` stereotype, so the
JPA entity is `ServiceEntity` and the class that holds catalog logic is
`ServiceCatalog`.

### 2. Gradle (Kotlin DSL) and Java 21, generated by Spring Initializr

The build comes from Spring Initializr rather than being written by hand, and the
Gradle wrapper is committed so no global Gradle install is needed. Java 21 is the
LTS already installed; moving to Java 25 later is a one-line toolchain change.
Maven would work equally well. Gradle wins on shorter build files.

### 3. PostgreSQL with Flyway and Spring Data JPA

- Flyway migrations own the schema and Hibernate only validates it
  (`ddl-auto=validate`), so every schema change is reviewed SQL rather than
  generated DDL.
- The `services` table has a surrogate `bigint` primary key and a unique `name`.
  The API identifies services by name and the id never leaves the persistence
  layer, but it keeps future references (deployments in Phase 2) and a possible
  rename feature cheap.
- `lifecycle` is a text column with a CHECK constraint, mapped to a Java enum.
- Timestamps are `timestamptz`, set by `ServiceCatalog` from an injected
  `java.time.Clock` so tests control time.
- `spring.jpa.open-in-view=false`, so no queries run outside the service layer.

Spring Data JDBC or `JdbcClient` would be simpler than JPA, but JPA is what most
Spring codebases use, and with one table and no relationships its usual pitfalls
(lazy loading, N+1 queries) don't come up. An in-memory database was rejected
because it behaves differently from PostgreSQL.

### 4. API conventions

- JSON over HTTP under `/api/v1`. Request and response bodies are Java records,
  separate from the JPA entity, so the API contract doesn't change when the table
  does. Lifecycle values are lowercase in JSON.
- Validation uses Jakarta Bean Validation on the request records. One regex,
  `^[a-z]([-a-z0-9]{0,61}[a-z0-9])?$`, covers names and owners.
- `lifecycle` arrives as a string and is validated like any other field. Binding
  it straight to the enum would make `beta` a generic malformed-body error
  instead of a field error on `lifecycle`.
- One `@RestControllerAdvice` extending Spring's `ResponseEntityExceptionHandler`
  (which already renders standard MVC errors as RFC 9457 problem details) adds the
  `errors` array for validation failures, 404 and 409 for the catalog's own
  exceptions, and a generic 500 that never echoes exception details.
- Duplicate names are caught by the database's unique constraint and turned into
  409, so the rule holds even if two requests race.
- Updates use `PUT` with the full set of editable fields. `PATCH` semantics
  (absent versus null fields) add complexity no client needs yet.
- Lists use Spring Data's `Pageable` (0-based pages, default size 20,
  `spring.data.web.pageable.max-page-size=100`), always sorted by name. They
  return a small `PageResponse` record instead of serializing Spring's `Page`,
  whose JSON shape isn't a stable contract.

### 5. API documentation generated by springdoc-openapi

springdoc-openapi 3.x (its Spring Boot 4 line) generates the OpenAPI document from
the controllers and serves Swagger UI. A hand-written, contract-first OpenAPI file
was rejected: the OpenSpec specs are already the agreed contract, and a second
hand-maintained one would drift.

### 6. Local runtime and tests

- `compose.yaml` defines PostgreSQL 18, and Spring Boot's Docker Compose support
  starts it on `./gradlew bootRun`.
- The application binds to `127.0.0.1` because it has no authentication. Setting
  `SERVER_ADDRESS` overrides this if it ever runs in a container.
- Integration tests use `@SpringBootTest` with MockMvc against a Testcontainers
  PostgreSQL that is shared across test classes, which keeps the suite fast. The
  "Database unreachable" health test gets its own container so stopping it doesn't
  break other tests, and the restart test starts the application twice against
  one container.
- Each spec scenario gets at least one test named after it (for example
  `rejectsDuplicateName`), so `/opsx:verify` and code review can go straight from
  a scenario to its test.
- Cross-cutting error behavior (`platform-api`) is tested through a small
  test-only controller, so it is verified before any catalog endpoint exists.

### 7. CI

A `build.yml` GitHub Actions workflow runs `./gradlew build` on Java 21 for pushes
to main and for pull requests. GitHub's Ubuntu runners include Docker, so
Testcontainers works there without extra setup.

### Later roadmap items this must not block

- **Service creation and repository provisioning (Phase 1):** these add columns
  such as the template used and the repository URL through new Flyway migrations.
  Service names are already valid GitHub repository names.
- **Kubernetes deployment (Phase 2):** names are valid Kubernetes resource names,
  including Service names, which must start with a letter. Owners are valid label
  values.
- **MCP server (Phase 4):** it can call the same REST API that the OpenAPI document
  describes.

## Risks / Trade-offs

- [No Docker runtime is installed yet] → Task 1.1 installs one, and the README
  lists it as a prerequisite.
- [Most Spring tutorials still target Boot 3; Boot 4 renamed some starters and
  moved test support into separate modules] → Generate the build with Initializr
  and follow the Spring Boot 4 reference docs instead of copying snippets.
- [JPA hides the SQL it runs] → `open-in-view` is off, and SQL logging can be
  turned on in tests when debugging.
- [Hard deletes drop history] → Acceptable while nothing references a service.
  Revisit when deployments (Phase 2) do.
- [There is no authentication] → The localhost-only binding limits exposure, and
  any change that exposes DevPlane beyond localhost must add authentication first.

## Open Questions

- Should owners become first-class teams with members, or stay plain identifiers?
  Decide when a feature needs more than a name, such as notifications in Phase 4.
  Nothing in this change depends on the answer.
